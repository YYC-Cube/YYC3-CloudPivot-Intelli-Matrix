## 二、发现的不足（按严重度分级）

| 级 | 不足 | 证据/影响 |
|---|---|---|
| **P1** | **无 CI/CD 发布链**：12 个容器全靠手工 docker 管理，代码→构建→部署无自动化；GitBucket 只是托管，没有 runner | 发布靠人记步骤，易出错、无回滚；这正是"自建部署服务"要补的环 |
| **P1** | **DB 写单点**：全部写入依赖 Mac 5433 主库，Mac 关机/外出 = 全网写入停摆（NAS 备库只读）；且无主库自动故障转移（replica 不会自动 promote） | 与"NAS 7×24"目标矛盾；需要明确的 failover 预案（哪怕是手动的 standby promote 手册） |
| **P2** | **两个存储池「可用 0 B」**：池空间 100% 分配给卷，卷内虽有剩余（4.3T/1.7T），但池无未分配余量，扩卷/建新卷必须先加盘 | 非紧急，但属于"知道才不慌"的容量事实；建议纳入监控阈值 |
| **P2** | **公网可达性缺环**：GitHub Pages 静态站与 Tailscale 内网 API 之间无通道；家庭外访客听不到音乐 | Tailscale Funnel（最快）或小 VPS 反代（最稳），二选一需决策 |
| **P2** | **音乐媒体落在冷存层**：693MB 在 Volume1（HDD RAID6 归档区），与"热负载专属 NVMe 卷"的分层约定不符 | 当前规模无感（并发≤几路流），但约定应当被遵守或显式豁免；建议显式记录"媒体读多写少，HDD 可接受" |
| **P3** | **备份链路未确认**：pg 是否有定时 base backup/pg_dump 出池？音乐媒体单副本在 NAS（RAID6 保硬件，不保误删/勒索） | 待确认；建议 3-2-1 最小实现：pg_dump 定时 + 媒体目录快照/异地 |
| **P3** | **复制监控未见告警**：流复制 lag 无证据接入了 Alertmanager | lag>阈值无人知 = HA 形同虚设 |

## 四、自建部署服务（补 P1 发布链）

**推荐方案：GitHub Actions 自托管 Runner（NAS）+ 部署密钥隔离**

理由：仓库已在 GitHub、CI 已在跑（ci.yml），加 runner 是**增量**不是换轨；GitBucket 继续当内网镜像/灾备仓，不折腾。

```
开发者 push → GitHub Actions (现有 ci.yml)
                 ├─ 测试/构建 (云端, 现状不变)
                 └─ deploy job (self-hosted runner@NAS, main 分支触发)
                      → rsync 产物 → NAS compose 目录
                      → docker compose up -d --build
                      → healthcheck 回读 /healthz, 失败自动 rollback
```

- Runner 以独立低权用户运行，只持有部署目录写权限（不碰卷数据）
- secrets 存 GitHub（DB 连接串、SSH key），不进仓库
- 回滚策略：镜像打 git-sha tag，compose 引用上一 tag 即回滚
- **备选**（未来若去 GitHub 化）：GitBucket + Woodpecker CI，现在不必

**DB 故障转移手册（补 P1 写单点，先手册后自动）**：
1. 手动版（立即可做）：一页 runbook——检测主库失联 → NAS 备库 `pg_ctl promote` → 切 music-api 写连接串 → Mac 回来后以新主为源重建复制
2. 自动版（中期）：repmgr 或 patroni； patroni 对现有架构改动大，建议 repmgr 起步

## 七、部署实测记录（2026-10-10 凌晨，全部实测通过）

**最终形态**：`yyc3-music-api` 容器 @ NAS，`network_mode: host` + `user: "501:101"`，代码目录 `/Volume1/yyc3_hd/music-api/`（compose 管理），镜像 `yyc3-music-api:latest`（node:20-alpine 两段构建，daocloud 镜像源 + npmmirror registry）。

**端到端验证（Mac 经 Tailscale 100.65.172.88:3113 实测）**：

| 用例 | 结果 |
|---|---|
| `GET /healthz` | ✅ `{"status":"ok","db":"up","mediaReady":true}` |
| `GET /api/music/albums` | ✅ 14 专辑，读 NAS 备库 5433 |
| `GET /tracks?album=<中文>` + `?q=` | ✅ URL 编码后过滤/搜索正常 |
| `GET /stream/:id` 整流 | ✅ 200，4,361,421 字节，audio/mpeg |
| `GET /stream/:id` Range | ✅ 206，bytes=1000000-1000999 恰好 1000 字节 |
| `POST /tracks/:id/play` | ✅ play_count 3→4，经 Tailscale 写转发 Mac 主库（NAS 备库只读） |
| 目录穿越探测 | ✅ `..%2F` 被 uuid 校验拦截，无文件泄露 |

**部署期两个环境级发现（写入 runbook）**：
1. **docker bridge 回环不做 SNAT**：容器访问宿主自己的 LAN IP，pg 看到的源是网桥地址 172.24.0.2，触发 `no pg_hba.conf entry`。NAS hba 只信 192.168.3.0/24，而 NAS 的 sudo 对数据卷有 root-squash 限制改不了 hba → 改 `network_mode: host`，源 IP 落在已有信任网段。
2. **TOS 启用 SMACK 安全模块**（lsm 含 smack/ima/evm）：POSIX 权限显示 other::r-x，但非属主进程读媒体目录一律 EACCES，仅 root 与属主 uid 501 可读 → compose 固定 `user: "501:101"`（免 root），同时保留镜像内非 root 默认值以适配其他环境。
